## Key ideas
- Postgres supports multiple indexing types that're optimized for different query patterns
- B-tree supports the majority of use cases (equality checks, range queries, sorting, and null checks)
- If you don't have a specific reason for using other methods, B-tree is the way to go
- Hash indexes are purely for equality comparisons. They don't support range queries or sorting.
- Hash is best for very large tables with frequent equality-only lookups. This will save a bit of index space (Probably won't need it for this project)
- GIN is designed for values that contain multiple elements (e.g. arrays). 
- They index every element within a single value, so GIN's best used for querying within JSONB or searching arrays
- GiST is best used for ranges & full-text search. It's also good with spatial data
- BRIN works best for very large, append-only tables with naturally ordered data (e.g. logs, events, or time-series data)
- Composite indexes cover more than one column
- They're most useful when you frequently filter or sort by multiple columns together
- The order of columns matter. (e.g. "city, last name" filters by city first, and can also filter by a last name within that city)
- Leftmost prefix rule is where a composite index can only be used if the queries include the leftmost column(s)
- So, place the most selective columns first when deciding column order (narrows the results most)
- A partial index only covers a subset of rows in a table. Useful when you only want to look at a specific portion of the data (e.g. an orders table, you frequently look at pending orders, and rarely at completed ones)
- This leads to smaller indexes, which use less disk space & memory, and are more maintainable
- Expression indexes index the result of functions/expressions (e.g. LOWER() expression on a value)
- You can create an index on the expression itself, and use that for indexes
- Unique indexes ensure no two rows have the same value in indexed columns
- This enforces data integrity & provides fast lookups
- Functionally identical to the UNIQUE constraint since it rejects duplicate value inserts, but a unique index explicitly focuses on query performance
- You can list all indexes, check the size of them, find unused indexes, drop them, and rebuild them
- Every INSERT, UPDATE, or DELETE must update every index on the table (If a table has 10 indexes, an insert query will make Postgres perform 11 write operations)
- This significantly slows down data modification on write-heavy tables 
- On large tables, indexes can take up as much space as the table itself
- Frequently used indexes are stored in memory, which can push useful data out of the cache & slow down other queries
- Indexes need periodic maintenance as data's added to tables, which adds complexity to schema migrations
- Index columns that appear in WHERE, JOIN, and ORDER BY clauses
- Monitor index usage regularly, & rebuild bloated indexes periodically (Tables with heavy update/delete activity causes bloat)
- Don't index every column since that'll slow down writes & consume storage
- Measure queries before & after indexing with EXPLAIN ANALYZE
