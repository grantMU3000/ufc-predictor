## Key ideas
- Alembic can view the status of your database to compare against the table metadata, and generate "obvious" migrations based on comparison
- To use autogenerate, env.py has a target_metadata field that can access a table's metadata
- This script also has functions for running migrations online, so using a revision --autogenerate command will autogenerate a file with the changes you need
- You still need to manually run it, so it's ALWAYS worth adjusting the migration file if necessary (Autogenerate isn't perfect)
- Autogenerate can't detext name changes, anonymous constraint names, or special SQLAlchemy types
- There are autogenerate plugins that you can add or removed depending on what you want autogenerate to detect (e.g. CHECK constraint by name)
- Alembic-utils adds autogenerate support for PostgreSQL
- alembic-postgresql-enum adds autogenerate support for Enums in Postgres
- If there's multiple MetaData collections within your application, target_metadata can track them all as a collection
- There are scenarios where you need to do data-backed migrations (New column with historical values, refactoring, normalization, etc.)
- You could use a script to do this, but migrations help with versioning & repeatability
- To do the migration upgrade: Add a nullable column, then fill existing data, and finally make it NOT NULL if need be
- Don't scan millions of rows in a single transaction during migration (Leads to timeouts, failed deployments, and locking tables)
- Use batching instead like looping over 10k rows per commit
